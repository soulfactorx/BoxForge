# BoxForge 설계 문서

Docker를 쉽게, 눈으로 보면서 다루기 위한 컨테이너 GUI. 데스크톱 앱(Windows · Linux · macOS)과, 같은 화면을 브라우저로 내주는 웹 서버 두 가지 모양으로 나간다.

- 상태: 구현 반영판 (0.17 기준). 처음의 계획서(v0.4)를 실제로 만든 것에 맞춰 다시 쓴 것이다.
- 계획과 달라진 점은 각 절에 적고, 아직 없는 것은 12절에 모았다.

---

## 1. 목표와 우선순위

| 순위 | 목표 | 의미 |
|------|------|------|
| 1 | **쉽다** | Docker 개념을 몰라도 쓸 수 있다. "무엇을 하고 싶은가"로 시작하고, 오류와 이상 상태는 원인과 해결책으로 풀어서 보여준다. |
| 2 | **보인다** | 컨테이너 · 이미지 · Compose · 볼륨 · 네트워크 · 빌드가 목록만이 아니라 그림(관계도 · 구조 · 사용량)으로 보인다. |
| 3 | **이것만 깔면 된다** | BoxForge만 있으면 Docker 엔진 설치(Windows는 WSL 2 포함)부터 첫 컨테이너 실행까지 앱이 한다. Docker Desktop은 쓰지 않는다. |
| 4 | **빠짐없다** | 자주 쓰는 `docker` 작업은 화면에서 된다. 화면에 없는 것은 내장 · 외부 터미널로 받는다. |
| 5 | **넓어진다** | Docker 말고도 Podman, containerd, Kubernetes를 같은 화면으로 다룬다. |

처음에는 혼자 쓰는 도구로 시작했다. 지금은 동료에게 권할 수 있도록 릴리스 · 자동 업데이트 · 사용자 문서를 갖췄다. 여전히 하지 않는 것: 사용자 계정과 권한 구분, 사용 정보 수집(텔레메트리), 유료 코드 서명 · 스토어 배포.

## 2. 핵심 설계 결정

| # | 결정 | 이유 |
|---|------|------|
| D1 | **Wails v2 (Go 백엔드 + React/TypeScript 화면), 실행 파일 하나** | 언어가 Go와 TS 둘뿐이고, OS의 웹뷰를 써서 가볍다. 설치 과정 없이 파일 하나를 받아 실행한다. |
| D2 | **화면이 부르는 것은 `internal/app.App`의 메서드뿐** | 데스크톱에서는 Wails 바인딩으로, 웹 서버에서는 HTTP로 같은 메서드를 부른다. 화면 코드는 `bridge.ts` 한 곳에서만 그 차이를 안다. 그래서 웹 서버 모드를 화면 수정 거의 없이 얹을 수 있었다. |
| D3 | **런타임 어댑터** (`engine.Runtime`) | 화면은 공통 모델만 본다. Docker · Podman은 Docker API 어댑터 하나로, containerd는 nerdctl 어댑터로, 테스트는 가짜 엔진으로 끼운다. |
| D4 | **상태는 엔진의 이벤트를 따라간다** | `hub`가 엔진의 이벤트를 구독해 목록을 다시 읽고 화면에 밀어 준다. 화면은 폴링하지 않으며, 터미널에서 `docker`를 직접 쳐도 곧 반영된다. 이벤트를 빠뜨리는 엔진(Kiri 등)을 위해 화면에서 무언가 한 뒤와 20초마다 한 번 더 읽고, 앱 이름 옆의 새로 고침 버튼으로 바로 다시 읽을 수도 있다. |
| D5 | **API 우선, CLI는 보조** | 엔진 API로 되는 것은 API로. Compose · 빌드 · 레지스트리 로그인처럼 클라이언트 쪽 로직이 큰 것만 `docker`(또는 `nerdctl`) 명령을 부른다. |
| D6 | **모든 조작에 같은 일을 하는 명령을 보여준다** | 화면 아래 표시줄과 기록에 `docker …` 명령이 남는다. 쓰다 보면 CLI가 익고, 문제가 생겼을 때 무엇을 했는지 그대로 전할 수 있다. |
| D7 | **Docker Desktop 배제, 무료 구성요소만** | Docker Desktop은 일정 규모 이상 기업에서 유료다. BoxForge는 Docker Engine · CLI · Compose · Buildx(모두 Apache-2.0)만 쓰고 엔진을 직접 설치한다. Docker Desktop의 엔진과 배포판은 찾는 대상에서 뺀다. |
| D8 | **엔진으로 가는 길에 네트워크 포트를 열지 않는다** | WSL 안의 엔진과 다른 PC의 엔진은 도우미 명령(`wsl.exe`, `ssh`)의 표준 입출력을 통로로 쓴다. |
| D9 | **되돌릴 수 없는 일은 무엇이 사라지는지 보여주고 확인받는다** | 삭제 · 정리 · 다시 만들기 모두. |

계획과 달라진 것: 화면 쪽 무거운 라이브러리(React Flow, elkjs, Monaco)는 쓰지 않았다. 관계도와 Compose 구조 그림은 직접 그린 SVG이고, 편집기는 일반 글상자다. 의존성은 React와 xterm.js(터미널), simple-icons(제품 아이콘)뿐이다.

## 3. 아키텍처

```
 데스크톱 앱 (main.go, Wails)                웹 서버 (cmd/boxforge-server)
 ┌──────────────────────────┐              ┌───────────────────────────────┐
 │ OS 웹뷰의 화면            │              │ 다른 기기의 브라우저            │
 └──────────┬───────────────┘              └──────────────┬────────────────┘
   Wails 바인딩 · 이벤트                     HTTPS: /api/call · /api/events(SSE)
            │                                 internal/webserver (로그인 · 세션)
            └───────────────┬───────────────────────┘
                            ▼
        internal/app.App   화면에 내놓는 메서드 전부 (얇게)
        ├─ hub             엔진 상태를 따라가며 화면에 푸시
        ├─ engines         엔진 찾기 · 고르기 · 연결 통로
        ├─ provision       Windows에 엔진 설치 · 관리 (WSL 2)
        ├─ clirunner       docker / nerdctl 명령 실행 (Compose · 빌드 · 로그인)
        ├─ update          릴리스에서 새 버전 받아 제자리 교체
        ├─ extterm         OS의 터미널 창 열기
        └─ desktop         Linux 앱 메뉴 등록
                            ▼
        internal/engine.Runtime   공통 모델과 인터페이스
        ├─ docker     Docker Engine API (Docker, Podman, Kiri 등 호환 엔진)
        ├─ nerdctl    containerd 단독: nerdctl 명령으로 구현
        └─ fake       메모리 안의 가짜 엔진 (화면 개발 · 테스트)
```

- **`app`**: 내보낸(대문자) 메서드 하나하나가 화면의 호출 하나다. 컨테이너 · 이미지 · 볼륨 · 네트워크, Compose(`compose.go`), 빌드(`build.go`), Kubernetes(`kube.go`, `forward.go`), 내보내기 · 가져오기(`bundle.go`), 업데이트 · 레지스트리 · 트레이(`product.go`).
- **긴 작업**: 내려받기 · 빌드 · 복사 · 내보내기는 진행을 이벤트(`pull`, `build`, `transfer`, `setup`)로 화면에 보낸다. 별도의 작업 관리자는 두지 않았다.
- **화면** (`frontend/src`): 쪽마다 파일 하나. `App.tsx`가 틀(사이드바 · 상태 표시줄 · 명령 기록)이고, `bridge.ts`가 Go 쪽과의 유일한 접점이다. 스타일은 `style.css` 하나(배치 규칙 + 그 위의 모양 층, 밝은 · 어두운 테마, 좁은 화면 규칙).

## 4. 엔진

### 4.1 고를 수 있는 엔진 (`internal/engines`)

| 종류 | 무엇 | 연결 방식 |
|------|------|-----------|
| 기본 | `docker` 명령이 쓰는 엔진 (`DOCKER_HOST`, 현재 context, 표준 소켓) | 소켓 직접 |
| Docker context | PC에 등록된 다른 context (Kiri, colima, Rancher Desktop 등) | 그 context의 주소 |
| WSL 배포판 | 배포판 안의 Docker Engine. Docker가 없고 nerdctl만 있으면 containerd로 | `wsl.exe -d <배포판> -u root -- docker system dial-stdio`의 표준 입출력 |
| 원격(SSH) | 다른 PC · 서버의 Docker Engine (`user@host[:포트]`, 키 로그인) | `ssh … docker system dial-stdio`의 표준 입출력 |
| Podman | Podman의 Docker 호환 API. 소켓이 켜져 있으면 그것을, 없으면 `podman system service`를 BoxForge가 켜서 | 유닉스 소켓 |
| containerd | Docker 없이 containerd만 있는 환경 (Linux · macOS, `nerdctl` 필요) | `nerdctl` 명령 |

고른 엔진은 설정 파일에 기억한다. 엔진 사이에는 이미지 · 볼륨 · 컨테이너를 복사할 수 있다(한쪽에서 읽어 다른 쪽에 넣는다).

TCP를 쓰지 않는 데는 보안 말고 기능상 이유도 있다. WSL의 localhost 중계는 연결의 한쪽 닫기(half-close)를 전하지 못해 `docker run`의 출력이 사라진다.

### 4.2 Windows에 엔진 설치 (`internal/provision`)

Windows에는 Linux 컨테이너를 직접 돌릴 방법이 없으므로 WSL 2 안에 엔진을 둔다. 사용자의 기존 배포판은 건드리지 않고 **BoxForge 전용 배포판**을 만든다.

1. WSL 2 준비: 없으면 설치한다(관리자 승인 한 번, Windows 재시작이 필요할 수 있음).
2. Linux 내려받기: Ubuntu · Debian(Microsoft의 배포 목록에서) 또는 Alpine 가운데 고른다. Docker를 설치할 수 있는 것만 보여준다. 받은 파일은 SHA-256으로 확인한다.
3. `wsl --import BoxForge …`로 전용 배포판을 만든다.
4. 그 안에 Docker Engine을 설치한다(Ubuntu · Debian은 apt, Alpine은 apk).
5. 엔진을 시작하고 연결한다.

설치 화면은 단계 목록과 진행 · 로그를 보여주고, 실패한 단계는 다시 시도할 수 있다. "엔진 제거"는 전용 배포판을 통째로 지운다.

설치 뒤의 관리(설정 화면):

- **앱을 닫아도 엔진 유지**: WSL은 쓰는 프로세스가 없으면 배포판을 내린다. 켜 두면 배포판 안에 지킴이를 두어 컨테이너가 계속 돈다.
- **엔진 자원**: WSL 가상 머신의 메모리 · CPU · 스왑 상한을 `%UserProfile%\.wslconfig`의 `[wsl2]`에 쓴다. 그 세 키만 고치고 나머지 줄과 줄바꿈 방식은 그대로 두며, 원래 파일은 `.wslconfig.boxforge-backup`으로 남긴다. WSL 전체의 설정이라 적용하려면 `wsl --shutdown`으로 모든 배포판을 멈춰야 하므로, "저장만"과 "지금 적용"을 고르게 한다.
- **디스크 자동 줄이기**: WSL의 가상 디스크는 지운 만큼 줄지 않는다. `wsl --manage BoxForge --set-sparse true`(WSL 2.0 이상)로 지운 자리가 Windows로 돌아가게 한다. 디스크 파일의 크기도 보여 준다.
- **로그인할 때 시작**: 사용자의 시작 프로그램 목록(Windows는 레지스트리의 Run 키, Linux는 `~/.config/autostart`)에 `--hidden`으로 BoxForge를 넣는다. 그렇게 시작하면 창 없이 트레이에서 시작되고 엔진도 연결된다. 관리자 권한이 필요 없다. macOS는 아직 없다.
- **회사 네트워크**: 프록시 주소와 사내 루트 인증서를 엔진에 넣는다. 프록시는 BoxForge 자신의 내려받기와 새로 만드는 Kubernetes 클러스터에도 쓴다. 인증서는 BoxForge가 사본을 보관했다가 클러스터에도 넣는다(7절).
- **경로 변환**: 폴더를 연결하거나 빌드할 때 `C:\…`를 `/mnt/c/…`로 바꾼다.

계획과 달라진 것: 명명된 파이프와 `boxforge` Docker context, `daemon.json` 편집, Windows용 Docker CLI 내려받기는 만들지 않았다.

### 4.2.1 Linux · macOS에 엔진 설치 (`provision/native.go`)

- **Linux**: 설치 스크립트 하나를 root로 돌린다. root는 이미 root이거나, 데스크톱의 비밀번호 창인 `pkexec`로 얻는다(둘 다 없으면 터미널 안내로 대신). Debian · Red Hat 계열은 Docker의 공식 설치 스크립트(get.docker.com)를, Alpine은 `apk`, Arch는 `pacman`을 쓴다. 서비스를 켜고 부팅 때 켜지게 하며, 사용자를 `docker` 그룹에 넣는다. 그룹은 다음 로그인부터 적용되므로 그 경우 다시 로그인하라고 알린다.
- **macOS**: 엔진이 macOS에서 직접 돌지 않으므로 Homebrew로 Colima와 docker 명령을 설치하고 `colima start`를 한다. Homebrew가 없으면 설치하지 않고 안내한다. 계획했던 Lima 직접 내려받기 대신 이 방식을 택했다.

### 4.3 containerd (`internal/engine/nerdctl`)

containerd에는 Docker 같은 API가 없고, 이름 · 포트 · 볼륨 · 네트워크를 갖춘 컨테이너를 만들어 주는 것은 nerdctl이다. 그래서 이 어댑터는 모든 일을 `nerdctl` 명령으로 한다. nerdctl의 출력이 Docker의 모양을 따르기 때문에 가능하다.

- **터미널**: nerdctl은 진짜 터미널을 요구한다. 그 기기의 `script` 명령이 빌려주는 터미널에서 돌리고, 크기는 밖에서 `stty`로 맞춘다.
- **변경 알림**: containerd의 이벤트에 어댑터 자신의 알림을 더한다(nerdctl의 볼륨 · 네트워크는 containerd 이벤트에 없다).
- **멈춘 컨테이너의 파일**: `nerdctl export`가 주는 전체 파일 묶음에서 골라 읽는다.
- **nerdctl의 한계를 피하는 곳**: `run -i`는 입력이 끝났음을 컨테이너에 전하지 못하는 일이 잦아, 볼륨에 데이터를 넣을 때는 도우미 컨테이너를 먼저 띄우고 `exec -i`로 넣는다. 이름을 바꾼 컨테이너는 그 이름을 다른 컨테이너가 쓰면 지워지지 않아, "다시 만들기"는 옛 컨테이너를 이미지로 보관 → 삭제 → 새로 만들기 순서로 한다.
- **안 되는 것**: 이미 있는 컨테이너의 네트워크 연결 · 해제(nerdctl에 명령이 없다. "설정 바꿔 다시 만들기"로 대신한다).

## 5. 쉽게 만드는 장치

Docker가 어려운 이유는 대개 (a) 용어, (b) 플래그가 많은 `run`, (c) 리소스 사이의 보이지 않는 관계, (d) 불친절한 오류다.

- **홈**: 실행 중인 것 요약, 자주 쓰는 프로그램 바로 실행(PostgreSQL · MySQL · MariaDB · Redis · MongoDB · nginx), 살펴볼 것(실패한 컨테이너와 이유), 디스크 사용량과 정리, 용어 한눈에.
- **실행 창**: `docker run`의 플래그를 칸으로 바꿨다(이미지, 이름, 포트, 저장 공간, 환경변수, 꺼졌을 때, 실행 명령, 네트워크). 이미지가 선언한 포트와 데이터 폴더를 읽어 "그대로 채우기"를 권하고, 비어 있는 필수 값은 짚어 준다. 아래에 같은 일을 하는 `docker run` 명령이 실시간으로 나온다.
- **셸만 있는 이미지**: alpine · ubuntu처럼 기본 명령이 셸뿐인 이미지는 터미널 없이 실행하면 바로 끝난다. 이런 이미지는 자동으로 터미널을 연 채(`-dit`) 실행하고 이유를 알려 준다.
- **설정 바꿔 다시 만들기**: 포트 · 볼륨 · 환경변수 · 네트워크는 만들 때만 정할 수 있다는 것을 초보자가 가장 자주 모른다. 지금 설정이 채워진 실행 창을 열어 같은 이름으로 다시 만들고, 실패하면 원래 것을 되돌린다.
- **찾기(Ctrl+K)**: 화면 · 컨테이너 · 이미지로 이동. `docker run …` 명령을 붙여넣으면 풀어서 실행 창에 채운다.
- **왜 멈췄나**: 컨테이너 상세가 종료 코드를 말로 풀고(메모리 부족, 명령 없음, 직접 중지 등) 마지막 로그로 이어 준다.
- **같은 일을 하는 명령과 기록**: D6.
- **확인 창**: 삭제 · 정리 전에 사라지는 것을 나열한다. 실행 중인 컨테이너가 쓰는 이미지는 지우지 못하게 하고 누가 쓰는지 알려 준다.

## 7. Kubernetes

컨테이너 엔진과 모델이 달라서 `Runtime`에 넣지 않고 따로 두었다. 구현은 단순하다.

- **클러스터**: 컨테이너 하나로 도는 단일 노드 k3s(`boxforge-k3s`, 특권 컨테이너, 데이터는 볼륨 `boxforge-k3s`). 화면의 스위치로 만들고 끄고 지운다. API 서버는 이 PC에서만 닿게(`127.0.0.1`) 6443번에 열고, 엔진의 다른 컨테이너나 이 PC의 프로그램이 이미 쓰고 있으면 다음 빈 포트(6464까지)를 쓴다. 저장하는 kubeconfig도 그 포트를 가리킨다.
- **k3s 인자**: `server --disable-network-policy --node-name boxforge --kube-proxy-arg=masquerade-all=true`. masquerade-all: 엔진의 기계에 `br_netfilter` 모듈이 없으면 같은 브리지의 파드끼리 서비스 주소(DNS 10.43.0.10 포함)로 보낸 요청의 답이 브리지로 곧장 와서 버려진다. 서비스 주소로 가는 것을 늘 노드 주소로 바꿔 보내면 모듈 없이도 된다. 네트워크 정책 기능(kube-router)은 마지막으로 기록된 노드 주소로 네트워크 장치를 찾는데, 엔진이 컨테이너를 다시 시작하면 주소가 바뀌어 클러스터가 켜지지 않는다("failed to find interface with specified node ip"). 작은 기계에는 메모리도 아낀다. 노드 이름을 고정해 컨테이너를 다시 만들어도 같은 노드다.
- **만든 방식 표시**: 컨테이너에 라벨 `dev.boxforge.k3s`(지금 `3`)를 단다. 꺼진 클러스터가 다른 방식으로 만들어졌으면 켤 때 컨테이너만 지우고 다시 만든다(볼륨의 상태는 그대로). 예전 이름의 노드는 지운다.
- **다른 클러스터**: 같은 엔진에 BoxForge가 만들지 않은 k3s 컨테이너(Kiri가 자기 Kubernetes 기능으로 만드는 `kiri-k8s` 등)가 있으면 화면에 알린다. 둘은 별개라 함께 켜면 자원을 두 배로 쓴다. BoxForge는 남의 클러스터를 다루지 않는다.
- **조회와 조작**: 모두 그 컨테이너 안의 `kubectl`을 엔진의 exec로 부른다. client-go 같은 새 의존성이 없고, 어느 엔진 위에서도 똑같이 동작하며, 화면이 보여주는 명령이 실제로 실행한 명령과 같다. 목록은 주기적으로 다시 읽는다(변경 감시가 아님).
- **기능**: 파드 · 워크로드 · 서비스 · 주소(Ingress) · 설정값(ConfigMap · Secret) · 저장소(PVC) · 경고 이벤트, 로그, 파드 터미널, describe, 삭제(무엇이 사라지는지 보이고 확인), 개수 조절, 다시 시작, YAML 적용, kubeconfig 보기. 설정값과 저장소의 목록은 그 탭을 연 동안만 읽는다(읽기마다 클러스터 안에서 명령 하나).
- **앱 배포 도우미**: 이미지 · 이름 · 파드 개수 · 포트 · 실행할 명령(`sh -c`) · 터미널을 연 채로 두기(`stdin` · `tty`) · 환경변수 · 넣을 설정값 · 접속 방법(없음 / 클러스터 안 이름 / 주소) · 저장소 크기를 받아 Deployment(+ Service, Ingress, PVC) YAML을 만들고, 보여 주고, 적용한다. "YAML로 고치기"로 그 글을 YAML 적용 창에 넘길 수 있다. 셸만 실행하는 이미지(엔진의 이미지 설명으로, 없으면 alpine · ubuntu 같은 이름으로 판단)는 터미널을 연 채로 두기를 미리 켠다: 그러지 않으면 바로 끝나 CrashLoopBackOff가 된다.
- **고치기**: 워크로드 · 서비스 · 주소 · ConfigMap은 지금 클러스터에 있는 것을 YAML로 받아(`kubectl get -o json`에서 상태 · id · 시각 · apply가 남긴 주석을 빼고 YAML로) 적용 창에 띄우고, 고친 것을 `apply`한다. 지우지 않고 바뀐다. Secret은 값을 화면에 보내지 않으므로 고치기가 없다.
- **엔진의 이미지 넣기**: 클러스터는 이미지를 스스로 받는다. 엔진에 있는 이미지는 `docker save`를 클러스터 컨테이너의 `ctr -n k8s.io images import -`로 흘려 넣을 수 있다(이 PC에서 빌드만 한 이미지도 쓸 수 있다). 기본으로는 하지 않는다: 대부분은 클러스터가 받을 수 있고, 작은 기계에서는 복사가 느리다(엔진이 이미지를 어디서 왔는지 알려 주지 않아, containerd 저장소의 Docker는 만든 이미지에도 digest를 붙인다). 배포 창에서 켜면 넣고 `imagePullPolicy: IfNotPresent`로 배포하고, 켜지 않았는데 파드가 이미지를 받지 못하면(ErrImagePull) 배포 진행에 "이 PC의 이미지를 클러스터에 넣고 다시 해 보기"가 나온다(`KubeLoadFor`: 넣고, IfNotPresent로 고치고, rollout restart).
- **컨테이너에서 배포**: 컨테이너 메뉴의 "Kubernetes로 배포"는 그 컨테이너의 이미지 · 이름 · 포트 · 환경변수 · 터미널 여부로 배포 도우미를 채운다. 명령은 옮기지 않는다(Kubernetes의 `command`는 이미지의 entrypoint를 대신한다). 볼륨의 데이터도 옮기지 않는다.
- **배포 진행**: 적용한 Deployment(적용 결과의 `deployment.apps/이름 created|configured` 줄)를 따라가며, 파드마다의 상태와 그 앱에 대한 클러스터 이벤트(파드를 만듦, 이미지를 받는 중, 컨테이너를 시작함 등)를 쉬운 말로 보여 준다. 따라가는 동안은 목록을 2.5초마다 읽는다. 보내는 동안에는 지난 초를 보이고, 보내기(apply · create)는 5분까지 기다린다.
- **화면을 떠나도**: 읽어 둔 목록, 보내는 중인 배포, 따라가는 배포는 화면 밖에 보관해, 다른 화면에 갔다 와도 그대로 보인다. 목록을 처음 읽기 전에는 "없음" 대신 읽는 중이라고 보인다.
- **흐름 그림**: 워크로드마다 주소(Ingress) → 서비스(selector가 워크로드 라벨과 맞는 것) → 워크로드 → 파드를 한 줄로 보인다. 준비된 파드가 모자라면 그 파드의 원인을 적고, 보낼 파드가 없는 서비스(selector 실수)는 따로 알린다.
- **원인 설명**: 파드가 안 돌 때, 컨테이너의 대기 메시지나 마지막 종료 이유, 아니면 그 파드에 대한 가장 최근 경고 이벤트를 쉬운 말과 함께 보인다(FailedScheduling, FailedMount 등은 뜻을 붙인다).
- **Secret**: 목록에서 값을 지우고 키와 크기만 화면에 보낸다(`kubectl apply`가 남기는 주석도 지운다). 만들 때는 `kubectl create`를 써서 값이 주석에 남지 않게 하고, 하단 명령 줄에도 값은 `****`로 보인다.
- **주소 열기**: k3s의 입구(Traefik, kube-system의 80번)를 이 PC의 8080번에 포트 연결로 잇는다. `*.localhost`는 브라우저가 이 PC로 보내므로 `이름.localhost:8080`으로 열린다.
- **포트 연결**: 클러스터의 주소는 밖에서 닿지 않는다(엔진이 WSL이나 다른 PC에 있을 수 있다). BoxForge가 이 PC의 포트를 듣고, 연결마다 클러스터 컨테이너의 네트워크를 함께 쓰는 도우미 컨테이너에서 `nc`를 돌려 엔진 연결을 통해 바이트를 나른다.

- **준비 여부**: 노드가 Ready인지는 클러스터 안의 `kubectl`로 묻는데, 느린 기계에서는 몇 초씩 걸리고 가끔 답이 없다. Ready였던 답은 15초 동안 다시 묻지 않고, 답이 없을 때는 2분 안에 Ready였으면 그대로 Ready로 본다(같은 컨테이너일 때). 화면은 목록을 5초마다 읽는다.
- **켜는 동안의 로그**: 켜기를 누르면 클러스터 컨테이너의 로그를 `kube-log` 이벤트로 화면에 보낸다(k3s · kubelet 줄은 "수준: 내용"으로 줄여서). 기다리는 동안 지난 시간과 단계(API 서버 시작 / 노드 준비)도 보인다. 느린 기계를 위해 컨테이너가 살아 있는 동안 25분까지 기다리고, 컨테이너가 멈추면 바로 멈췄다고 알린다. 화면을 떠났다 와도 "아직 시작하는 중"과 로그(`KubeLogTail`)가 보이고, 꺼진 클러스터는 꺼지기 전의 마지막 로그를 보인다.
- **사내 인증서**: 클러스터는 이미지를 스스로 받으므로, 사용자가 추가한 인증서를 클러스터 컨테이너의 인증서 목록에 더하고(원래 목록의 사본에 매번 다시 더한다) 목록이 바뀌었으면 클러스터를 다시 시작한다.

- **Compose 프로젝트 옮기기**: 프로젝트 화면의 "Kubernetes로 옮기기"는 `docker compose config`(Compose 자신이 정리한 설정)를 읽어 매니페스트를 만든다(`kube_compose.go`). 프로젝트마다 네임스페이스 하나(서비스끼리 Compose에서처럼 이름으로 찾게), 서비스마다 Deployment(entrypoint → `command`, command → `args`, environment, tty · stdin_open, working_dir, deploy.replicas)와 포트가 있으면 같은 이름의 Service(ports의 target과 expose), 이름 붙은 볼륨마다 PVC(1Gi), 이름 없는 볼륨 · tmpfs는 emptyDir. 옮기지 못하는 것(이 PC의 폴더, 값 없는 환경변수, TCP 아닌 포트, depends_on, healthcheck, privileged 등)은 YAML에 넣지 않고 "옮기면서 달라지는 것"으로 알린다. 빌드하는 이미지(`프로젝트-서비스`)는 엔진의 것을 클러스터에 넣는다(`IfNotPresent`). 볼륨의 데이터는 옮기지 않는다. 적용과 진행은 Kubernetes 화면에서 하며, 진행은 네임스페이스를 따라간다.

BoxForge가 만든 클러스터만 다룬다. 임의의 kubeconfig는 없다. 만드는 것은 모두 `default` 네임스페이스에 둔다.

## 8. 내보내기 · 가져오기 (`.boxforge`)

컨테이너를 다른 PC로 옮기거나 동료에게 주기 위한 파일. zip이며(크기를 모르는 부분을 받는 대로 쓸 수 있다) 안에는:

```
manifest.json           무엇이 들었는지 (형식 번호, 만든 버전, 엔진 종류)
containers/<n>.json     엔진이 준 컨테이너 설명(inspect) 그대로
images/<n>.tar          이미지 (docker save 형식). "바뀐 파일 포함"이면 지금 상태를 이미지로 만든 것
volumes/<이름>.tar       볼륨 데이터
```

가져올 때는 이미지 넣기 → 볼륨 채우기 → 컨테이너 만들기(시작하지 않음) 순서로 한다. 같은 이름의 볼륨이나 컨테이너가 이미 있으면 건드리지 않고 알린다. Docker와 containerd는 설명의 모양이 조금 달라서, 각 어댑터의 `CreateFrom`이 상대의 설명도 읽는다. 엔진 사이의 복사도 같은 부품을 쓴다.

파일에는 환경변수(비밀번호 포함)와 볼륨 데이터가 그대로 들어간다. 화면에서 이를 알린다.

## 9. 웹 서버 (`cmd/boxforge-server`, `internal/webserver`)

엔진이 있는 기기에서 켜 두고 휴대폰이나 다른 PC의 브라우저로 쓰기 위한, 창 없는 BoxForge. 창 라이브러리가 필요 없어 순수 Go로 빌드하며, 화면 파일은 실행 파일 안에 들어 있다. 사용법은 [SERVER.md](SERVER.md).

로그인한 사람은 엔진 전체를 다루고, 그것은 그 기기의 관리자 권한과 같다. 그래서:

- 로그인 없이 답하는 것은 화면 파일과 로그인 · 세션 확인뿐이다.
- 비밀번호는 PBKDF2 해시로 저장한다. 한 주소에서 5번 틀리면 1분 잠근다.
- 세션은 `HttpOnly` · `SameSite=Strict` 쿠키. 서버를 다시 켜면 모두 끝난다.
- 두 번째 비밀번호(보기 전용)로 들어온 세션은 읽기만 하는 메서드의 정해진 목록만 부를 수 있다. 목록에 없는 것은 모두 거절하므로, 새 메서드는 일부러 넣기 전에는 보기 전용에게 닫혀 있다.
- 다른 사이트의 페이지가 보낸 요청(`Origin` 불일치)은 거절한다.
- 암호화 없이는 네트워크에 열리지 않는다(`-tls`로 직접 만든 인증서, 또는 가진 인증서, 또는 앞단 프록시가 맡는다는 명시).
- 서버의 화면에 창을 띄우는 일(외부 터미널, 엔진 설치)은 거절한다.

서버의 폴더나 파일을 골라야 하는 곳(Compose 프로젝트 폴더, 빌드할 폴더 등)에서는, 운영체제의 파일 창이 없으므로 화면이 서버의 폴더 목록을 받아 직접 고르는 창을 그린다(`Browse`, 보기 전용 계정에는 닫혀 있다).

브라우저에서는 파일이 서버가 아니라 그 기기로 가야 하므로, "저장"과 "내보내기"는 서버의 임시 폴더에 쓴 뒤 브라우저가 한 번 받아 가고(받으면 지움), "가져오기"는 브라우저가 올린다.

실행 방법: 터미널에서 그대로, `-daemon`(새 세션으로 떼어 내 백그라운드, 출력은 `~/.config/BoxForge/server.log`, 서버가 자기 프로세스 번호를 `server.pid`에 적고 `-stop` · `-status`가 그것을 씀), 또는 `-install`(root: `/opt/boxforge`에 두고 그 사용자의 것으로, docker 그룹, 비밀번호 · 인증서 준비, systemd 단위나 OpenRC 스크립트를 만들어 켬. `-uninstall`은 서비스만 지움). `-update`는 화면의 자동 업데이트와 같은 부품(체크섬 확인, 실행 중인 파일은 옆으로 옮기고 새 파일을 그 이름에)으로 바꾼 뒤, `-daemon`으로 돌던 서버는 저장해 둔 옵션(`server.args`)으로 다시 켜고, 서비스면 서비스를 다시 켠다. 임시 폴더는 사용자마다 따로다(`/tmp/boxforge-server-<uid>`). Windows에서는 `-daemon`만 되고 서비스 설치는 아직 없다.

개발용 `cmd/devserver`는 같은 패키지를 로그인 없이 쓰며 127.0.0.1에만 열린다.

## 10. 업데이트와 릴리스

- **릴리스**: `main`에 올라온 `wails.json`의 버전이 아직 릴리스되지 않았으면 GitHub Actions가 빌드하고 태그와 릴리스를 만든다. 순서는 [RELEASING.md](RELEASING.md).
- **앱의 업데이트** (`internal/update`): GitHub의 최신 릴리스를 보고, 이 기기에 맞는 파일을 받아 `checksums.txt`의 SHA-256과 맞으면 실행 중인 파일을 `.old`로 옮기고 그 자리에 둔다. 다음에 켤 때(또는 "다시 시작") 새 버전이 뜬다. 데스크톱 앱과 서버는 각자의 파일로 업데이트한다.
- **주의한 점**: Linux는 실행 파일을 옮긴 뒤 "내 경로"를 물으면 옮겨진 이름을 답한다. 그래서 경로는 시작할 때 한 번만 묻는다. 서버는 같은 인자로 제자리에서 다시 시작한다(유닉스는 프로세스 교체).

## 10.5 언어

화면의 글은 컴포넌트 안에 한국어로 적혀 있다. 영어는 글마다 조회 함수를 끼우는 대신, 그려진 화면을 옮기는 방식으로 낸다(`frontend/src/i18n.ts`). 표(`i18n/en.json`)가 한국어 글을 영어로 잇고, 관찰자가 React가 화면에 올리는 글자 노드와 라벨을 바꿔 쓴다. React는 화면이 아니라 자신이 마지막에 요청한 값과 비교하므로 방해받지 않는다.

- 표는 `scripts/extract-strings.cjs`가 소스에서 뽑은 글(JSX 글, 문자열, 채워 넣는 자리가 있는 글은 `{0}` 꼴, Go 쪽이 화면에 보내는 한국어)을 키로 한다. 글을 더하거나 고치면 이 스크립트가 번역이 없는 것을 알려 준다.
- 문장이 값과 조각으로 나뉘어 화면에 올라가는 곳은 조각 단위로 옮겨지므로 영어 어순이 어색할 수 있다.
- 터미널 · 로그 · 편집기처럼 사용자나 프로그램이 쓴 글은 건드리지 않는다.
- 고른 언어는 브라우저(웹뷰)에 저장한다. 웹 서버에서는 접속한 사람마다 다를 수 있기 때문이다.

## 11. 보안

- 엔진을 다루는 것은 호스트의 관리자 권한과 같다. 데스크톱 앱은 네트워크 포트를 열지 않는다(Kubernetes 포트 연결은 사용자가 요청한 포트를 127.0.0.1에만 연다). 네트워크에 여는 것은 웹 서버뿐이며 9절의 장치를 갖는다.
- 관리자 권한은 Windows의 WSL 설치 단계에서만 요청한다. 앱은 일반 권한으로 돈다.
- 내려받는 것(Linux 배포 파일, 업데이트)은 정해진 배포처에서 받고 체크섬을 확인한다.
- 레지스트리 로그인은 `docker login`에 맡긴다. 비밀번호는 명령줄이 아니라 표준 입력으로 넘기고, 앱이 따로 저장하지 않는다.
- 명령은 셸을 거치지 않고 인자 배열로 실행한다. 원격 주소처럼 사용자가 준 값은 옵션으로 읽히지 않는 모양인지 확인한다.
- 사용 정보를 어디에도 보내지 않는다. 밖으로 나가는 것은 업데이트 확인(GitHub)과 사용자가 시킨 내려받기 · Docker Hub 검색뿐이다.

## 12. 아직 없는 것

계획에 있었거나 요청받았지만 만들지 않은 것.

| 것 | 사정 |
|----|------|
| 코드 서명 | 인증서가 없다. 릴리스 작업에 Windows 서명 단계는 있고, 인증서를 넣으면 동작한다. macOS는 임시 서명 |

| 웹 서버의 사용자 계정 | 비밀번호 둘(관리용 · 보기 전용)뿐, 사람별 계정은 없다 |
| 화면이 없는 명령을 위한 범용 폼, 커버리지 검사 | 터미널로 대신한다 |
| 한국어 · 영어 밖의 언어 | 영어는 화면을 그리면서 옮기는 방식(10.5절)이라 표만 더하면 다른 언어도 된다 |

확인이 덜 된 곳: 실제 Windows에서의 프록시 · 인증서 · 엔진 유지 · 엔진 자원 · 디스크 자동 줄이기 · 로그인할 때 시작, 실제 Mac에서의 실행과 Colima 설치, 실제 Linux 데스크톱에서의 pkexec 설치, 실제 휴대폰에서의 사용감, WSL 안의 containerd, 사내 인증서를 넣은 클러스터가 실제 회사망에서 이미지를 받는지. 개발 환경에서 실행해 볼 수 없어 흐름만 확인했다.

## 13. 저장소 구조

```
BoxForge/
├─ main.go  tray*.go  wails.json   데스크톱 앱: 창, 트레이, 파일 대화상자
├─ cmd/
│  ├─ boxforge-server/             웹 서버 (창 없음)
│  └─ devserver/                   개발용 서버 (로그인 없음, 127.0.0.1)
├─ internal/
│  ├─ app/                         화면에 내놓는 메서드
│  ├─ engine/                      공통 모델과 Runtime 인터페이스
│  │  ├─ docker/  nerdctl/  fake/  어댑터
│  ├─ engines/                     엔진 찾기 · 고르기 · 연결 통로 · 설정 파일
│  ├─ hub/                         엔진 상태 따라가기
│  ├─ provision/                   Windows 엔진 설치 · 관리
│  ├─ clirunner/                   docker / nerdctl 명령 실행
│  ├─ webserver/                   HTTP · 로그인 · TLS
│  ├─ update/  version/            자체 업데이트
│  ├─ extterm/                     외부 터미널
│  └─ desktop/                     Linux 앱 메뉴 등록
├─ frontend/
│  ├─ embed.go                     빌드된 화면을 실행 파일에 넣기
│  └─ src/                         React 화면. bridge.ts가 Go 쪽과의 접점
├─ build/                          아이콘
├─ docs/                           DESIGN · SERVER · RELEASING
└─ .github/workflows/              ci.yml, release.yml
```

테스트: 순수한 로직은 Go 단위 테스트. 화면은 `devserver`(실제 Docker 또는 가짜 엔진)에 Playwright로 붙어 확인한다. nerdctl 어댑터에는 실제 containerd를 상대로 도는 테스트가 있다(`BOXFORGE_NERDCTL_IMAGE`를 주면 실행). Windows 전용 동작은 대역 스크립트(`BOXFORGE_WSL`, `BOXFORGE_SSH`)로 흐름만 확인한다.

## 14. 참고: Kiri

[libracoder/kiri](https://github.com/libracoder/kiri)(Apache-2.0)는 BoxForge를 만들게 된 계기다. 소스를 읽고 정리한 내용.

Kiri는 Docker GUI가 아니라 **자체 컨테이너 엔진**이다. `dockerd`를 쓰지 않고 Docker Engine API를 Rust로 다시 구현했으며, 창은 그 엔진에 딸린 부속이다.

| | Kiri | BoxForge |
|---|---|---|
| 정체 | Docker Desktop을 대체하는 엔진 + 간단한 창 | 진짜 엔진들 위의 완전한 GUI |
| 엔진 | Docker API 재구현 (빠르고 가벼움) | `dockerd` · Podman · containerd 그대로 |
| 구현 | Rust, OS별 웹뷰 + 단일 HTML | Go + Wails + React |
| 강점 | 속도, 메모리, 설치 경험 | 조작의 폭, 시각화, 초보자 안내 |

Kiri의 **엔진**은 rename · commit · tag · save/load · network connect 등을 지원하지만 **창**에는 그 경로가 없다. "이름 변경조차 안 된다"는 것은 엔진이 아니라 창이 얇아서이고, BoxForge는 그 간격을 메우려는 것이다.

가져온 것: `wsl.exe` 표준 입출력 중계(TCP 배제), 단계가 보이는 설치 화면, 컨테이너 표의 Compose 묶음 · 상태 필터 · 이미지 아이콘 · 포트 링크, 사이드바의 엔진 카드, 컨테이너 하나로 뜨는 k3s, Compose 프로젝트 상세의 구성. Kiri가 화면의 실행 버튼에서 모든 이미지를 터미널을 연 채로 실행한다는 것도 소스에서 확인했고, BoxForge는 셸만 있는 이미지에 한해 같은 방식을 쓴다.

가져오지 않은 것: 자체 엔진과 VM, 공유 링크, 다국어, 이름 · 로고 · 디자인.

Kiri의 엔진은 Docker context로 등록되므로 BoxForge에서 그대로 고를 수 있다. Kiri 엔진이 아직 구현하지 않은 API는 BoxForge에서도 실패하며, 몇 군데는 그 차이를 피해 간다(컨테이너 크기를 주지 않으면 이미지 크기로 대신, 볼륨은 도우미를 실행해야 붙음 등).
